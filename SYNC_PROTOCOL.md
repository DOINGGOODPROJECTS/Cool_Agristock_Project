## 1. Overview

Cool AgriStock implements an **offline-first** inventory management system for agricultural cooperatives in Côte d'Ivoire. Field agents and warehouse operators record stock movements on devices that may have intermittent or no connectivity. The sync layer ensures:

- Operations recorded offline are delivered exactly once to the server.
- Concurrent operations from multiple devices are detected and surfaced as conflicts rather than silently overwriting each other.
- Every action on every operation is permanently recorded in an append-only audit log.
- The system is resumable: a client that crashes mid-sync can safely re-send its entire pending queue.

The protocol is implemented across three layers:

| Layer | Technology | Entry point |
|-------|-----------|-------------|
| Client | JavaScript (`SyncManager.js`) + IndexedDB | Browser PWA |
| Server API | Laravel + MySQL | `POST /api/sync/push` |
| SMS fallback | Africa's Talking webhook | `POST /webhook/sms` |

## 2. Glossary

| Term | Definition |
|------|-----------|
| **Op** | An `inventory_ops` row — a single immutable record of a stock movement |
| **op_id** | UUID v4 generated by the client; globally unique; used for idempotency |
| **logical_seq** | Lamport timestamp, integer, monotonically increasing per device |
| **device_id** | String identifying the originating device, e.g. `web-{uuid}` or `sms:+2250700000000` |
| **sync_status** | Current lifecycle state of an op: `pending`, `applied`, `conflict`, `superseded`, `cancelled` |
| **Conflict** | An op the server received but could not safely apply due to a concurrent change or negative-stock projection |
| **Authoritative state** | The server's confirmed `inventory_stock.quantity` after processing a push batch |
| **Reconciliation** | The server-side process of validating, applying, and logging each op |
| **Session** | One push call; recorded in `sync_sessions` |

## 3. Core Concepts

### 3.1 Device Identity

On first boot, each client generates and persists a device ID:

```
device_id = "web-" + UUID_v4()          // Browser PWA
device_id = "sms:" + E.164_phone        // SMS interface
device_id = "web"                       // Server-generated ops (merge, override)
```

The device ID is stored in `localStorage` (browser) and never changes for the lifetime of the installation. It is included in every op and every push session request so the server can exclude a device's own ops from pull responses.

### 3.2 Lamport Clock

Each client maintains a monotonically increasing integer counter, `logical_seq`, persisted in `sync_meta` (IndexedDB) under the key `logical_seq`.

**Rules:**

1. Before recording any op, increment `logical_seq` by 1.
2. After a successful `push` response, advance the local clock:
   ```
   logical_seq = max(local_logical_seq, server_logical_seq)
   ```
3. After a successful `pull` response, apply the same rule.
4. The clock must never decrease.
5. Two ops from the same device must never share the same `logical_seq`.

The server does not re-order ops. It processes them in the array order received. The `logical_seq` is stored on the op for causal ordering and conflict diagnosis; it is not used as a primary sort key by the reconciliation engine.

**Clock skew:** Two devices may have wildly different clocks. A device with `logical_seq = 3` and a device with `logical_seq = 99 999` are both valid. The server stores each device's clock value as-is and does not normalise across devices.

### 3.3 Op Schema

Every op in the push body must include these fields:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `op_id` | UUID v4 | Yes | Client-generated unique identifier |
| `user_id` | Integer | Yes | `users.id` of the actor |
| `device_id` | String (≤191) | Yes | Device identifier (see §3.1) |
| `logical_seq` | Integer ≥ 0 | Yes | Lamport clock value at time of recording |
| `storage_id` | Integer | Yes | `storages.id` |
| `product_id` | Integer | Yes | `products.id` |
| `stock_id` | Integer \| null | No | `stocks.id`; required for stock mutation side-effects |
| `op_type` | Enum | Yes | One of: `stock_in`, `stock_out`, `adjustment`, `spoilage`, `transfer`, `correction` |
| `quantity_delta` | Decimal | Yes | Signed quantity change in `unit`; negative for outflows |
| `unit` | String (≤50) | Yes | Unit of measure, e.g. `kg`, `t`, `sac` |
| `notes` | String (≤500) \| null | No | Free-text annotation |
| `client_created_at` | ISO-8601 datetime \| null | No | Wall-clock time on the device |

**Op type semantics:**

| `op_type` | `quantity_delta` sign | Side effect |
|-----------|----------------------|-------------|
| `stock_in` | Positive | None beyond `inventory_stock` update |
| `stock_out` | Negative | Creates `releases` row (if `stock_id` present) |
| `adjustment` | Either | Triggers concurrent-adjustment conflict detection |
| `spoilage` | Negative | Creates `rottens` row (if `stock_id` present) |
| `transfer` | Either | No additional side effect |
| `correction` | Either | No additional side effect |

### 3.4 Op State Machine

```
                 ┌─────────────────────────────────────────────────────┐
                 │                   Client Queue                       │
                 │  [queued locally]  ─── sync() ──►  POST /api/sync/push
                 └─────────────────────────────────────────────────────┘
                                            │
                              Server reconciliation
                                            │
                      ┌─────────────────────┼─────────────────────┐
                      ▼                     ▼                      ▼
                  APPLIED             CONFLICT             ALREADY_SEEN
                      │                     │                  (no new row)
              inventory_stock         awaits manager
               updated; audit:         resolution
               submitted+applied         │
                                ┌────────┴──────────┐
                                ▼                    ▼
                           SUPERSEDED           APPLIED
                          (discard/merge)    (accept/override)
                                │                    │
                           audit:                audit:
                           discarded/merged     accepted/overridden
```

**States stored in `inventory_ops.sync_status`:**

| Status | Meaning |
|--------|---------|
| `pending` | Received by server, not yet processed (transient) |
| `applied` | Accepted and applied to `inventory_stock` |
| `conflict` | Received but not applied; awaits manager resolution |
| `superseded` | Replaced by a newer op (via edit or merge); terminal |
| `cancelled` | Explicitly cancelled before application; terminal |

## 4. Reconciliation Algorithm

The reconciliation engine processes each op in the push batch sequentially, inside a single database transaction. The batch fails atomically if the transaction is rolled back.

### 4.1 Idempotency Check

```
IF inventory_ops WHERE op_id = $op['op_id'] EXISTS:
    return ALREADY_SEEN          ← no insert, no side effects
```

A client may safely re-send its entire pending queue on retry. Ops the server has already seen are acknowledged without duplication.

### 4.2 Conflict Detection

Two conflict conditions are checked in order:

**Condition 1 — Concurrent adjustment:**

```
IF op_type = 'adjustment':
    rival ← inventory_ops
        WHERE storage_id  = $op.storage_id
          AND product_id  = $op.product_id
          AND op_type     = 'adjustment'
          AND sync_status = 'applied'
          AND (last_sync_at IS NULL OR applied_at > last_sync_at)
        ORDER BY applied_at DESC
        LIMIT 1

    IF rival EXISTS:
        conflict_reason       = "Concurrent adjustment already applied since last sync."
        conflict_with_op_id   = rival.op_id
        → CONFLICT
```

`last_sync_at` is the client's timestamp of its previous successful sync, passed in the push body. If omitted (null), the engine searches all applied adjustments for that product+storage regardless of time.

**Condition 2 — Negative stock projection:**

```
current_qty ← inventory_stock
    WHERE storage_id = $op.storage_id
      AND product_id = $op.product_id
      AND (stock_id  = $op.stock_id  OR stock_id IS NULL)
    COALESCE(quantity, 0)

projected = current_qty + $op.quantity_delta

IF projected < 0:
    conflict_reason = "Projected quantity {projected} would be negative
                       (current: {current_qty}, delta: {op.quantity_delta})."
    → CONFLICT
```

If neither condition triggers, the op proceeds to application.

### 4.3 Stock Application

```
IF op.stock_id IS NULL:
    skip stock update        ← op is still marked 'applied'; no stock mutation
ELSE:
    UPSERT inventory_stock
        SET quantity        = current_qty + op.quantity_delta
            last_op_id      = op.op_id
            last_updated_at = NOW()
        WHERE storage_id = op.storage_id
          AND product_id = op.product_id
          AND stock_id   = op.stock_id

    IF op.op_type = 'spoilage' AND detail EXISTS:
        INSERT rottens (before_qty, qty, after_qty, detail_id, stock_id)

    IF op.op_type = 'stock_out' AND detail EXISTS:
        INSERT releases (before_qty, qty, after_qty, delivery='Client', detail_id, stock_id)
```

After stock application, the op's `sync_status` is set to `applied` and `applied_at` is recorded.

## 5. Queue Actions and State Transitions

All actions are gated by RBAC (see §7) before the engine runs the state check.

### accept

```
REQUIRES: sync.accept permission
REQUIRES: op.sync_status = 'conflict'

→ applyOpToStock(op)
→ op.sync_status       = 'applied'
→ op.resolved_by       = actor.id
→ op.resolved_at       = NOW()
→ op.applied_at        = NOW()
→ audit: 'accepted'
```

### discard

```
REQUIRES: sync.discard permission
REQUIRES: op.sync_status = 'conflict' (enforced in UI; server does not re-check)

→ op.sync_status       = 'superseded'
→ op.resolved_by       = actor.id
→ op.resolved_at       = NOW()
→ audit: 'discarded'
```

### merge

```
REQUIRES: sync.merge permission (Admin only)
REQUIRES: opA and opB exist

→ opA.sync_status      = 'superseded'
→ opB.sync_status      = 'superseded'
→ merged_op created with merged_quantity, edited_from_op_id = opA.op_id
→ applyOpToStock(merged_op)
→ merged_op.sync_status = 'applied'
→ audit: 'merged' for opA, 'merged' for opB, 'applied' for merged_op
```

### override

```
REQUIRES: sync.accept permission
REQUIRES: op.stock_id IS NOT NULL

→ inventory_stock.quantity = override_quantity  (force-set, not delta)
→ audit: 'overridden'
```

### cancel

```
REQUIRES: sync.cancel permission AND (actor.id = op.user_id OR actor.group_id = 1)
REQUIRES: op.sync_status = 'pending'  ← throws 422 if not pending

→ op.sync_status       = 'cancelled'
→ op.cancelled_by      = actor.id
→ op.cancelled_at      = NOW()
→ audit: 'cancelled'
```

### edit

```
REQUIRES: sync.edit permission AND (actor.id = op.user_id OR actor.group_id = 1)
REQUIRES: op.sync_status = 'pending'  ← throws 422 if not pending

→ op.sync_status          = 'superseded'
→ new_op created (copy + changes, new op_id, status = 'pending',
                  edited_from_op_id = op.op_id)
→ audit: 'edited' on original op
→ returns new_op.op_id
```

### 6.2 POST /api/sync/push

Push a batch of pending ops to the server.

**Permission required:** `sync.push`

**Request body:**

```json
{
  "session_id":   "uuid",
  "device_id":    "web-abc123",
  "last_sync_at": "2026-06-01T10:00:00Z",   // nullable — client's last successful sync
  "ops": [
    {
      "op_id":             "uuid",
      "user_id":           42,
      "device_id":         "web-abc123",
      "logical_seq":       17,
      "storage_id":        194,
      "product_id":        5,
      "stock_id":          null,
      "op_type":           "stock_in",
      "quantity_delta":    50.0,
      "unit":              "kg",
      "notes":             null,
      "client_created_at": "2026-06-01T09:55:00Z"
    }
  ]
}
```

**Response 200:**

```json
{
  "session_id":          "uuid",
  "applied_count":       1,
  "conflict_count":      0,
  "already_seen_count":  0,
  "conflicts": [],
  "authoritative_state": [
    {
      "storage_id": 194,
      "product_id": 5,
      "stock_id":   null,
      "quantity":   150.0,
      "unit":       "kg"
    }
  ],
  "server_logical_seq": 1024
}
```

**Conflict object shape (inside `conflicts[]`):**

```json
{
  "op_id":              "uuid",
  "conflict_reason":    "Projected quantity -50.000 would be negative ...",
  "conflict_with_op_id": null,
  "storage_id":         194,
  "product_id":         5,
  "stock_id":           null,
  "op_type":            "stock_out",
  "quantity_delta":     -100.0,
  "unit":               "kg",
  "product":            { "id": 5,   "name": "Banane" },
  "storage":            { "id": 194, "name": "Entrepôt Abidjan – Yopougon" }
}
```

**Client behaviour on success:**

1. `logical_seq = max(local_logical_seq, server_logical_seq)`
2. Apply each entry in `authoritative_state` to the local `inventory_stock` cache (overwrite optimistic values).
3. Remove all pushed `op_id`s from the local `pending_ops` queue.
4. If `conflicts` is non-empty, dispatch `sync:conflicts` DOM event.
5. Dispatch `sync:completed` DOM event.

**Client behaviour on failure (non-2xx):**

Leave the local queue intact. The same batch will be re-sent on the next online event. Idempotency guarantees no duplication.

### 6.3 GET /api/sync/pull

Fetch applied ops from other devices and the caller's pending conflicts.

**Permission required:** `sync.pull`

**Query parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `since_logical_seq` | Integer | Return only ops with `logical_seq > since_logical_seq` |
| `device_id` | String | Exclude ops from this device (caller's own ops) |

**Response 200:**

```json
{
  "remote_ops": [
    {
      "op_id":              "uuid",
      "user_id":            7,
      "device_id":          "web-other-device",
      "logical_seq":        900,
      "storage_id":         194,
      "product_id":         5,
      "stock_id":           null,
      "op_type":            "stock_in",
      "quantity_delta":     25.0,
      "unit":               "kg",
      "notes":              null,
      "applied_at":         "2026-06-01T11:00:00Z",
      "server_received_at": "2026-06-01T11:00:01Z"
    }
  ],
  "pending_conflicts": [ /* same shape as push conflicts[] */ ],
  "server_logical_seq": 1025
}
```

**Client behaviour on success:**

1. For each entry in `remote_ops`: add `quantity_delta` to the local `inventory_stock` cache (non-optimistic).
2. `logical_seq = max(local_logical_seq, server_logical_seq)`
3. If `pending_conflicts` is non-empty, dispatch `sync:conflicts` DOM event.

```json

```

**Response 200:**

```json
{
  "message":    "Resolved.",
  "op_id":      "uuid",
  "resolution": "accept"
}
```

### 6.5 POST /api/sync/cancel

**Request body:**

```json
{
  "op_id":  "uuid",
  "reason": "Optional cancellation note"
}
```

**Response 200:**

```json
{ "message": "Op cancelled.", "op_id": "uuid" }
```

**Response 422** (if op is not in `pending` status):

```json
{ "error": "invalid_state", "message": "Cannot cancel op [...]: status is [applied], only pending ops may be cancelled." }
```

### 6.6 POST /api/sync/edit

Edit a pending op. The original is superseded; a replacement pending op is created.

**Permission required:** `sync.edit` (owner or Admin only)

**Request body:**

```json
{
  "op_id": "uuid",
  "changes": {
    "quantity_delta": 75.0,
    "notes":          "Corrected after physical recount",
    "reason":         "Typo in original entry"
  }
}
```

**Response 200:**

```json
{
  "message":         "Op edited — replacement pending op created.",
  "original_op_id":  "uuid-original",
  "new_op_id":       "uuid-replacement"
}
```

**Response 422** (if op is not `pending`):

```json
{ "error": "invalid_state", "message": "Cannot edit op [...]: only pending ops may be edited (status: applied)." }
```

| sync.edit | ✅ all | ✅ own | ✅ own | ✅ own | ✅ own | ✅ own | ✅ own | ✅ own | ✅ own |
| sync.merge | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |

**"own" = the action is permitted only when `actor.id = op.user_id`.  Admin (group 1) bypasses the ownership check for all `own`-restricted actions.**

**Enforcement:** All API routes are protected by `SyncPermissionMiddleware` which returns:

```json
// HTTP 403
{ "error": "forbidden", "message": "...", "action": "sync.accept" }
```

Owner-restricted actions (cancel, edit) pass the middleware but the engine performs a secondary `canOwnerOrFail()` check and returns HTTP 403 JSON for non-owners.

## 8. Audit Log Schema

Table: **`sync_audit_log`** (append-only; rows are never updated or deleted)

| Column | Type | Description |
|--------|------|-------------|
| `id` | Integer PK | Auto-increment |
| `op_id` | UUID | References `inventory_ops.op_id` |
| `actor_id` | Integer | `users.id` of the person who triggered the action |
| `actor_group_id` | Integer | Denormalised group at time of action |
| `action` | Enum | One of 11 action values (see below) |
| `before_value` | JSON \| null | Snapshot of relevant state before the action |
| `after_value` | JSON \| null | Snapshot of relevant state after the action |
| `reason` | String \| null | Human-readable explanation |
| `device_id` | String | Device that triggered the action |
| `ip_address` | String \| null | Server-side IP (null for SMS) |
| `created_at` | Timestamp | Wall-clock time on the server |

**Action values:**

| Action | When written |
|--------|-------------|
| `submitted` | Op received by server for the first time |
| `applied` | Op successfully applied to `inventory_stock` |
| `conflict_flagged` | Op stored as conflict instead of being applied |
| `accepted` | Manager accepted a conflicted op |
| `discarded` | Manager discarded a conflicted op |
| `cancelled` | Owner or admin cancelled a pending op |
| `edited` | Owner or admin edited a pending op (written on original) |
| `merged` | Admin merged two conflicting ops (written on both originals) |
| `overridden` | Manager force-set stock quantity |
| `superseded` | Op replaced by a newer version (edit or merge) |
| `reconciled` | One entry per push session, anchored to the first processed op |

**Guarantee:** For every op that enters the system, at minimum a `submitted` entry and either an `applied` or `conflict_flagged` entry will exist in `sync_audit_log`.

## 10. SMS Interface

Field agents without smartphones can submit stock ops via SMS to shortcode **20098** (Africa's Talking sandbox; production shortcode to be approved by ARTCI).

### Command Format

```
<COMMAND> <quantity> [kg] <product_name> <storage_code>
```

| Command | Op type | Delta sign |
|---------|---------|-----------|
| `ENTREE` / `ENTRÉE` | `stock_in` | Positive |
| `SORTIE` | `stock_out` | Negative |
| `POURRI` / `POURRIE` | `spoilage` | Negative |
| `AJUSTER` / `AJUSTÉ` | `adjustment` | Positive |

Commands are case-insensitive and accent-insensitive.

**Examples:**

```
ENTREE 50 kg tomates S1
SORTIE 12 manioc S2
POURRI 8 kg bananes S1
AJUSTER 150 kg ignames S3
```

### Storage Codes

`S1` maps to the storage with the lowest `storages.id`, `S2` to the second-lowest, etc. The mapping is stable as long as storage rows are not deleted.

### Product Matching

Product names are matched case- and accent-insensitively against `products.name`. Both full and partial matches are accepted (bidirectional substring match).

### Webhook Flow

```
1. Africa's Talking  →  POST /webhook/sms
                         { from, to, text, date, id }

2. Signature verification
   header: X-AT-Checksum = base64(HMAC-SHA256(raw_body, AT_WEBHOOK_KEY))
   If AT_WEBHOOK_KEY is unset → verification skipped (dev/sandbox mode)

3. Phone normalisation → E.164
   Look up member_phones WHERE phone = normalised_number
   If not found → reply "Numéro non enregistré…" → HTTP 200

4. Permission check: sync.push
   If denied → reply "Accès refusé…" → HTTP 200

5. SmsParser.parse(text)
   If null → reply "Format non reconnu…" + help text → HTTP 200

6. ReconciliationEngine.processBatch([op], user, session)
   device_id = "sms:{phone}"

7. Reply via Africa's Talking SDK:
   Applied  → "✓ AgriStock: {type} de {qty} kg enregistrée. Ref: {op_id[:8]}"
   Conflict → "⚠ AgriStock: {type} de {qty} kg reçue mais en CONFLIT…"
   Duplicate→ "AgriStock: Opération déjà reçue (doublon)…"
```

The webhook always returns `HTTP 200` to Africa's Talking regardless of the business outcome. SMS reply failures are logged but never surface as 5xx responses.

## 11. Resumability Guarantee

A client that crashes, loses power, or drops its connection at any point during a sync cycle can safely resume by re-sending its entire pending queue. The server guarantees:

1. **No duplicates.** Any op whose `op_id` already exists in `inventory_ops` returns `ALREADY_SEEN` without creating a new row, without re-applying stock, and without writing a new audit entry.

2. **Idempotent session.** `sync_sessions` uses `firstOrCreate` on `session_id`. If the same session_id is re-submitted, the existing session row is reused. Session counters (`ops_applied`, etc.) are updated correctly on the second run because `ALREADY_SEEN` ops are excluded from the counts.

3. **Client queue drain.** On a successful push (HTTP 200), the client removes all ops in the batch from its local `pending_ops` store, regardless of whether each op was `APPLIED` or `ALREADY_SEEN`. The `CONFLICT` result does not block the drain — conflicted ops are now server-side and tracked via `pending_conflicts` in the next pull response.

4. **Clock monotonicity.** After any successful server interaction (push or pull), the client advances its `logical_seq` to `max(local, server_logical_seq)`. It is therefore impossible for a re-sent op to arrive with a `logical_seq` lower than the server's current max — the client will have incremented past it.

## 12. Error Codes

| HTTP | Code field | Meaning |
|------|-----------|---------|
| 401 | — | Unauthenticated (invalid/missing Sanctum token) |
| 401 | — | SMS webhook: invalid AT signature |
| 403 | `forbidden` | RBAC permission denied; `action` field names the gate |
| 403 | `forbidden` | Ownership check failed (cancel/edit on another user's op) |
| 422 | `invalid_state` | Attempted cancel or edit on a non-pending op |
| 422 | — | Laravel validation failure; `errors` object present |
| 500 | — | Unhandled server error (should never occur in normal operation) |

All error responses from sync endpoints include `Content-Type: application/json`.
